## Summary

Reviewed `git diff ba95329..HEAD -- entity/Target.lua core/selftest.lua` (commits 65c33d7 feat +
6f22a48 test; the two docs commits are out of file scope). The change adds `obj.clear()` inside
`macroTorch.Target:new()` — a macro-callable `macroTorch.target.clear()` that wipes every
`[spell][currentMobName]` entry from `macroTorch.context.immuneTable` and
`macroTorch.context.definiteBleedingTable` (which are live references to the per-class `SM_EXTEND`
saved-variable sub-tables), silently no-ops when there is no target or an empty name, and prints at
most one aggregate confirmation. Category R selftests (R-01 wipe + unrelated-mob survival + single
message; R-02 empty-name skip) are registered with `isOptional=true`.

The feature contract is correctly implemented: no critical findings. Two warnings (test-hygiene
global leakage, unguarded type assumption over persisted data) and two info items follow.

## Placement / Architecture Verdict: Target.lua is the correct home

**Responsibility split.** The codebase already draws a clean line through this exact territory:
`core/spell_trace_immune.lua` owns table *binding/lifecycle* (the two lazy loaders, lines 67-102),
while `entity/Target.lua` owns *per-mob record operations* — all five sibling methods mutate or read
the same two tables keyed by `obj.name`. `clear()` is functionally a batch form of `removeImmune`
(a record operation keyed by the current target name), so it belongs with its siblings. Moving it
to spell_trace would split record mutators across modules and force a target-name parameter into a
module whose callbacks deliberately consume `macroTorch.target` state at event time rather than
owning entity concerns. Verdict: correct placement, not a rubber stamp.

**Does direct scrubbing bypass invariants? No.** `loadImmuneTable`/`loadDefiniteBleedingTable`
(spell_trace_immune.lua:80-82, 99-101) are one-time lazy bindings — no pruning, no counters, no
other bookkeeping exists anywhere in the module. Mutating inner keys while pairs-iterating the
outer table is safe (only the outer table iteration is live). Empty spell-level sub-tables left
behind are byte-identical residue to what `removeImmune` already leaves; every reader
(`isImmune`/`isDefiniteBleeding` and all druid decision code in leveling.lua/combo.lua/cat.lua/
Druid.lua) treats a missing key as false, so there is no user-visible inconsistency. Skipping
`removeImmune` only suppresses its per-spell yellow chat line — the aggregate line preserves the
plan's "at most ONE chat line" requirement.

**Insertion-point regression safety.** The diff to Target.lua is purely additive (zero `-` lines):
siblings are byte-identical. `clear()` is an own key on the singleton, and `classMetatable`
`__index` (core/class.lua:21-34) only fires for missing keys, with `TARGET_FIELD_FUNC_MAP` empty and
no `clear` key in `UNIT_FIELD_FUNC_MAP` — resolution needs zero wiring. Grep-verified: no other file
in the repo iterates either context table, and all sibling callers (`spellsImmuneTracing` writer
side; druid decision reader side) only read per-mob truthiness, so a cleared mob simply reads
"fresh" — which is the feature's purpose.

**Lua 5.0 compliance.** No `#` operator, no `goto` in any added line; loops use `pairs`,
`macroTorch.tableLen`, `table.insert`. `git diff --check` exit 0 (LF clean). `bbcheck.js` prints
BALANCED for Target.lua; the MISMATCH on selftest.lua is the pre-existing checker limitation
documented in the plan (the diff-lines balance gate passed at execution time).

## Warnings

### WR-01: Category R tests leak six result variables into session globals

**File:** `core/selftest.lua:931-935, 964-965`
**Issue:** Inside the two pcall closures, `immLeft`, `defLeft`, `otherImm`, `otherDef`, `msgCount`
(R-01) and `survivor`, `msgCount` (R-02) are assigned without `local`. WoW's Lua has no strict
globals, so these are created in `_G` and persist for the whole session. This deviates from the
plan's own wording ("capture results into locals") and from the house CR-01 pattern established by
Category P tests (`local ok, pcallRes = true, true` declared above the pcall). `msgCount` and
`survivor` are generic identifiers with real cross-addon collision potential in the shared `_G`
namespace.
**Failure scenario:** Another addon uses a `_G.msgCount` global, or a developer re-runs the
selftest in-session (e.g. `/_mt` after resetting `macroTorch._selfTestRan` for debugging); the
assertions then read stale values from the previous run. The `assert(pcallRes, ...)` precedence
would still catch a pcall failure first, so this cannot mask a crash today — but the pollution is
unconditioned and session-permanent.
**Fix:** Declare the capture variables as locals above the pcall, mirroring the P-category style:

```lua
    local immLeft, defLeft, otherImm, otherDef, msgCount
    local pcallRes = pcall(function()
        target.clear()
        immLeft = ...
        ...
    end)
```

### WR-02: clear() indexes spell-level values without a type guard (persisted-data robustness)

**File:** `entity/Target.lua:92, 98`
**Issue:** Both scrub loops do `if mobTable[name] then` with no check that the spell-level value is
a table. All current writers (`recordImmune`/`recordDefiniteBleeding`) store sub-tables, and
legacy pre-player-class-layered data sits outside the bound sub-table, so this is unreachable with
today's schema. However, `SM_EXTEND` is a user-persisted saved variable that survives addon version
upgrades and hand-editing for years, and the sibling readers (`isImmune` line 30-31,
`isDefiniteBleeding` line 71-72) guard with `and` chains precisely because they distrust the
persisted shape. A single non-table entry (corrupted or hand-edited saved vars) makes the macro
throw "attempt to index" mid-wipe, leaving a partial clear and a red chat error.
**Failure scenario:** A user's `SM_EXTEND.immuneTable.DRUID` contains one malformed entry (e.g.
`["Moonfire"] = true` from manual editing). `macroTorch.target.clear()` throws on that key; records
for later spells are not cleared, and the aggregate confirmation never prints — the "escape hatch"
silently half-fails.
**Fix:** One guard per loop, cheap and consistent with the siblings' defensive style:

```lua
        for spellName, mobTable in pairs(macroTorch.context.immuneTable) do
            if type(mobTable) == 'table' and mobTable[name] then
                mobTable[name] = nil
                immuneCleared = immuneCleared + 1
            end
        end
```

(Note: the truthiness test itself matches `removeImmune`'s convention, and current values —
`GetTime()` numbers and `true` — are always truthy, so that part is not a defect.)

## Info

### IN-01: The "nothing removed" branch of clear() is untested

**File:** `core/selftest.lua:906-976`
**Issue:** R-01 always seeds records so both counters are ≥ 1; R-02 covers the empty-name guard.
The plan's third truth — "prints at most ONE line, and only when at least one record was actually
removed" — is only half-covered: a second `clear()` call (or a clear on a mob with no records)
must print nothing, but no test asserts that. The nil-name (no-target) production path also shares
R-02's guard branch via `not name` but is not directly exercised.
**Fix:** Inside R-01's pcall, after capturing `msgCount`, call `target.clear()` a second time and
assert `macroTorch.tableLen(shown) == 1` (i.e. `msgCount2 == msgCount`). Two lines, closes the gap.

### IN-02: R-01 registered isOptional=true — accepted contract, noted for the record

**File:** `core/selftest.lua:910, 947`
**Issue:** R-01 is the primary behavioral assertion for this feature, yet a failure renders as a
yellow warning rather than a red fail. This matches the plan's explicit registration contract and
the established stub-based-test precedent (Categories M, P, Q are all `isOptional=true`), so it is
accepted as-is.
**Fix:** None required. If future clear() regressions should hard-fail the selftest, flip R-01's
third argument to `false` — but that would break house convention.

## Regression-Safety Note

- The five siblings are byte-identical (diff is purely additive in Target.lua); insertion sits
  between `isDefiniteBleeding`'s `end` and the `isBeastOrDragonkin` comment, as the plan's anchor
  demanded.
- Call chains traced: `spellsImmuneTracing` (0.1s periodic) → `recordImmune`/`recordDefiniteBleeding`
  writes; druid leveling/combo/cat/Druid read `isImmune` truthiness only. A wipe makes those reads
  false — the intended semantics. WoW is single-threaded, so no interleaving hazard with the
  periodic tracer.
- Selftest isolation: R-01/R-02 snapshot via `rawget`, run under pcall, and restore (including the
  `''`-key seed in R-02) BEFORE any assert — CR-01 discipline holds for table/name/show state; the
  only residual pollution is the WR-01 globals. Category D (runs earlier) only reads
  `target.name`; druid-side tests registered later run against restored state. Tests skip silently
  when `macroTorch.context` is nil (early login).
- The test seeds use `__SELFTEST_CLEAR_*` keys that cannot collide with real spell/mob names, and
  both snapshot/restore target the current `context` table binding, so a loader re-bind mid-test
  cannot lose the restore.
