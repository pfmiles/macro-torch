# PLAN: tools/cpdamage.lua `--json-out` 严格 JSON 化（G-28-5 闭合）

## 目标

让 `lua tools/cpdamage.lua <SV> --json-out <file>` 产出的归档是**严格 JSON**（所有对象键为带引号字符串），Node 等严格解析器可无报错解析；同时为编码器补上自检断言（当前 selftest 完全没覆盖编码器），并保持 Lua 5.0/5.1/5.4 三个解释器上的 `--selftest` 全绿。终端/屏显报告输出逐字不变。

根因（G-28-5 记录）：`encodeValue` 的对象分支对数字键直接 `encodeScalar(k)`（如 `{"claw":{1:{"n":0}}}`），数字键裸奔——Lua 风味表记法，非严格 JSON，Node 在 position 57 拒绝。

用户决定 (b)：**给数字键加引号**（或数组化层级桶）。本计划选**加引号**分支：改动最小、文档结构逐字段不变（tier 桶保持 `"0".."3"` 键、batch 桶保持 `"1000"` 等键），不移动任何数据位置，任何已存在读取方不受结构变动影响。

## 锁定约束（必须遵守，违反即失败）

1. **只改一个文件**：`tools/cpdamage.lua`。其余仓库文件一律零触碰。
2. **屏显不变**：`printReport` / `printClawShredTable` / `printOocTable` / `printBiteLine` / `decisionLines` 及其所有 `io.write` 逐字不动。`encodeValue` 只被 `writeJsonOut`（1117 行）消费，修复天然不触及屏幕路径——但仍需 diff 口径门证明（见 Task 2 验证）。
3. **编码取加引号方案，不数组化**：`encodeKey` 数字键输出带引号十进制；不做 0..3 → 1 下标数组搬移。
4. **`encodeScalar` 一字不动**：其注释声明与游戏内 `macroTorch.jsonEncodeScalar` 契约同构（526-532 行），是值序列化契约；键处理走新增的 `encodeKey`，不动值契约。
5. **Lua 5.0 合规**：新增行不得含 `#` 长度运算符、`goto`、`::` label；只用 `string.format` / `tostring` / `math.floor` / `string.gsub` 等 5.0 既有特性。
6. **禁止运行任何构建脚本**（build.sh 等）；`SM_Extend.lua` 是构建产物，零触碰。`tools/` 目录不参与构建，运行三个 Lua 解释器做验证不违反此条。
7. **LF 行尾**：新增行保持 LF（仓库 `.gitattributes` 已约定）。

## 背景事实（来自本次实地读取 2026-09-13，编辑锚点以此为准）

- **编码器病灶在 `encodeValue` 对象分支，当前 597-599 行**：
  ```lua
      local parts = {}
      for k, val in pairs(v) do
          table.insert(parts, encodeScalar(k) .. ':' .. encodeValue(val, depth + 1))
      end
  ```
  数字键（tier 桶 0..3、batch 桶 1000/2000/3000）经 `encodeScalar` 输出为裸数字 → 非严格 JSON。`encodeScalar` 定义在 533-564 行，`encodeValue` 在 569-601 行；新 `encodeKey` 插在这两函数之间（564 行 `end` 之后、`encodeValue` 注释之前）。

- **decoder 是严格的**：`decodeJson` 的对象解析在 457-459 行强制 `string.byte ~= 34 → 'expected string key'`。因此 `decodeJson(encodeValue(x))` 往返即严格性探针——旧编码器吐出裸数字键会被自家 decoder 拒绝，新检查天然能 RED 捕获 G-28-5。
