### WR-01: SM_Extend.lua (generated build output) contains stale spellId values and assertions

**File:** `SM_Extend.lua:2574-2581, 3678-3698`
**Issue:** SM_Extend.lua is git-ignored and generated by `./build.sh`. The current build artifact still contains the OLD spell IDs:
- `Rake = 1822` (should be 9904)
- `Rip = 9492` (should be 9896)  
- `Ferocious Bite = 22557` (should be 31018)

And the OLD selftest assertions still reference these stale IDs. This means:
- Anyone who copies SM_Extend.lua to the SuperMacro directory without rebuilding will deploy broken spell ID mappings.
- `SpellTrace` will fail to match `UNIT_CASTEVENT` events for these spells until the first runtime correction kicks in (causing one-cast blind spots).
- Selftests will fail with assertion mismatches.

**Fix:** Run `./build.sh` to regenerate SM_Extend.lua from the updated source files. The file should then contain:
```lua
["Rake"] = 9904,
["Rip"] = 9896,
["Ferocious Bite"] = 31018,
```
And matching selftest assertions at lines 3678-3698.

### WR-02: `events.lua` unitId guard asymmetry — nil-guards removed from active code path

**File:** `core/events.lua:93`
**Issue:** The commented-out debug log block (lines 90-92) had a thorough nil-guard chain:
```lua
if unitId and macroTorch.player and macroTorch.player.guid and unitId == macroTorch.player.guid ...
```
The active code on line 93 uses a bare comparison:
```lua
if unitId == macroTorch.player.guid and castType == 'CAST' then
```
This drops the `macroTorch.player` and `macroTorch.player.guid` nil-guards. If `macroTorch.player` or its `guid` property is nil at the time `UNIT_CASTEVENT` fires, this will throw a Lua error. While `macroTorch.player` is typically always initialized by the time this event fires, the asymmetry with the debug block is a defensive coding regression.

**Fix:** Restore the nil-guard chain to match the debug block's safety level:
```lua
if unitId and macroTorch.player and macroTorch.player.guid and unitId == macroTorch.player.guid and castType == 'CAST' then
```

### WR-03: `isKeywordInEquippedItemTooltip` silently fails when tooltip scan frame already exists but has wrong owner

**File:** `biz_util.lua:366-369`
**Issue:** The lazy-init singleton pattern:
```lua
if not macroTorch._tooltipScanFrame then
    macroTorch._tooltipScanFrame = CreateFrame("GameTooltip", "MacroTorchTooltipScan", UIParent, "GameTooltipTemplate")
    macroTorch._tooltipScanFrame:SetOwner(UIParent, "ANCHOR_NONE")
end
```
checks for frame existence but does NOT re-validate `SetOwner`. If the frame was created in a previous session but `SetOwner` was lost (e.g., frame recycling in WoW), the tooltip will not populate correctly. This is low-risk (frame persistence is reliable in WoW), but could cause silent false-negatives where `isKeywordInEquippedItemTooltip` returns `false` for valid keywords.

**Fix:** Move `SetOwner` outside the lazy-init block so it always runs:
```lua
if not macroTorch._tooltipScanFrame then
    macroTorch._tooltipScanFrame = CreateFrame("GameTooltip", "MacroTorchTooltipScan", UIParent, "GameTooltipTemplate")
end
macroTorch._tooltipScanFrame:SetOwner(UIParent, "ANCHOR_NONE")
```

```lua
if unitId == macroTorch.player.guid and castType == 'CAST' then

```
